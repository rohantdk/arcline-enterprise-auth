arcline · Enterprise SSO & RBAC Bridge

How your login and data-isolation service works

A beginner's guide to every part of the project: what each piece does, how it does it, and why it is there. Written from the actual code in D:\Agentic AI Projects\arcline-enterprise-auth.

37 / 37 tests pass Tenant isolation verified on PostgreSQL Audit log is insert-only Local development only Okta / Entra ID, SAML not done
The brief Build an auth pipeline connecting the arcline AI stack to Okta / Azure AD via SAML or OIDC, with SCIM provisioning and row-level data scoping. Why it matters: large companies will not buy software unless their employees can sign in with the company account (single sign-on) and each customer's data is strictly kept apart from every other customer's.
In one sentence A FastAPI web service (main.py) lets employees sign in through Keycloak, checks their roles, only shows them documents from their own organization (enforced twice in Python and once more inside PostgreSQL), lets an identity provider add users automatically through SCIM, and records every allow or deny in a log nobody in the app can edit.

Process 1 · OIDC single sign-on

Logging in

What: An employee proves who they are to Keycloak, and the app gets a signed statement of their identity and roles. How: the OpenID Connect authorization code flow with PKCE, handled by the Authlib library.

Browser → App GET /auth/login

The app creates a random state value and a secret PKCE verifier, stores them in the session, and redirects the browser to Keycloak with the client ID, the callback address and a challenge made from the verifier.

Browser → Keycloak

You type your username and password into Keycloak's page. The app never sees them.

Keycloak → Browser → App GET /auth/callback?code=…

Keycloak sends you back with a short-lived one-time code. The app checks state matches, which blocks forged callbacks.

App → Keycloak server to server

The app trades the code for tokens, sending its client secret and the PKCE verifier. A stolen code is useless without both.

Keycloak → App

Keycloak returns an ID token signed with its private key. Authlib checks the signature with Keycloak's public key, found through the .well-known/openid-configuration discovery address.

App → Browser

The app saves sub (your permanent user ID), email, username and realm_access.roles into a signed session cookie, and records a login_succeeded audit event.

200 Login successful401 if anything fails · login_failed logged
Every later request

The browser sends the cookie automatically. get_current_user reads it; no cookie means 401 and an authentication_denied event. POST /auth/logout clears it.

Why it's built this way

Passwords stay in one hardened place (Keycloak). Swapping Keycloak for a customer's Okta or Entra ID later only changes configuration, because they all speak the same OIDC standard. PKCE and state close the two classic attacks on this flow: stolen codes and forged callbacks.

Process 2 · Role-based access control

Role checks

What: some pages are only for certain roles. How: a FastAPI dependency named require_role("admin") runs before the /admin endpoint and looks for admin in the roles saved at login.

Browser → App GET /admin

First get_current_user: is there a session at all?

no → 401
require_role("admin")

Is "admin" in the user's roles list?

no → 403 · role_authorization_denied logged
/admin

The endpoint runs and returns the admin dashboard.

200
Why a dependency

The rule is written once and attached to any endpoint with one line. It can't be forgotten halfway through a function, and every refusal is logged the same way.

Two limits to know: roles are global Keycloak realm roles, the same in every organization (the role column in the membership table isn't used for this yet). And roles are copied into the cookie at login, so removing someone's admin role only takes effect after they log in again.

Process 3 · Row-level data scoping

Data isolation between organizations

What: a member of organization A must never see organization B's documents, even though both live in the same tables. How: three independent walls. Any one of them alone would block the leak.

1app

Membership check

The app asks: is there a row in organization_memberships for this sub and this organization? If not: 403 and tenant_access_denied.

2app

Double filter

The document query filters by both document ID and organization ID, so guessing another company's document ID returns 404.

3database

PostgreSQL row-level security (RLS)

Before querying, the app tells PostgreSQL who is asking. Policies in schema.sql hide every row that doesn't match, no matter what SQL the app sends.

How wall 3 actually works

set_postgres_security_context

Runs set_config('app.current_user_sub', sub, true) and the same for app.current_organization_id. The true means "only for this transaction", so the value can't leak into someone else's request on a reused connection.

PostgreSQL policy on documents

A row is visible only if its organization_id equals the current organization and a membership exists for the current user in that organization.

If the app forgets step 1

The setting is empty, NULLIF turns it into NULL, and NULL never equals anything. Result: zero rows. The system fails closed.

Why three walls

Code changes over time, and one forgotten WHERE clause is the most common way multi-tenant apps leak data. With RLS, the database is the last line of defense. It only works because the app connects as arcline_app, which is not allowed to bypass RLS, and because the tables use FORCE ROW LEVEL SECURITY, so even the table owner is filtered.

Process 4 · SCIM 2.0 provisioning

Adding users automatically

What: when a company hires someone, their identity provider calls our SCIM endpoints to give that person access. How: a bearer-token-protected API that checks the user really exists in Keycloak, then links them to the configured organization as a member.

SCIM client → App POST /scim/v2/Users

Header Authorization: Bearer <SCIM_BEARER_TOKEN>. Compared with secrets.compare_digest, which takes the same time whether the guess is close or not, so attackers learn nothing from timing.

wrong token → 401
App validates the body

Must include the SCIM User schema, and userName must equal externalId, both being the Keycloak user ID (sub).

bad input → 400
App → Keycloak

Using a second Keycloak client, arcline-scim-verifier, the app gets its own token (client credentials flow) and asks the Keycloak Admin API whether that user exists. That client is only allowed view-users and query-users.

not found → 404Keycloak down → 503
App → PostgreSQL scim_provision_membership()

A database function owned by arcline_scim_writer checks the organization is the one allowed in scim_configuration (arcline-default), then inserts the membership with role member.

already there → 409created → 201
App

Records scim_user_provisioned or scim_user_provisioning_denied with the reason.

Why these choices

Role is always member: if the caller could choose the role, anyone holding the SCIM token could create admins. Keycloak check first: stops memberships for people who don't exist. Organization stored in the database: the caller can't point SCIM at another tenant.

EndpointDoes
GET /scim/v2/ServiceProviderConfigTells the identity provider which SCIM features exist (PATCH, bulk, filter, sort are all "not supported")
GET /scim/v2/UsersLists users in the configured organization, paged with startIndex and count (max 100)
GET /scim/v2/Users/{id}One user, or 404
POST /scim/v2/UsersProvisions the user, as above

Current limits: no PATCH or DELETE, so a person who leaves the company is never removed (deprovisioning is the main reason enterprises want SCIM). Real Okta sends an email as userName, not a Keycloak ID, so it won't work with Okta as-is.

Process 5 · Audit logging

Recording who did what

What: every login, logout, refusal, document read and SCIM action becomes a row in audit_events. How: the helper _record_audit_event filters the data, then calls a locked-down database function.

_record_audit_event

Rejects unknown event types and outcomes (success, failure, denied). Drops any metadata key except reason, required_role, resource, status_code, and cuts text to 120 characters. Tokens and personal data can't sneak in.

App → PostgreSQL record_audit_event()

The function runs with its owner's rights (arcline_audit_writer, which can only INSERT). It re-checks the same rules, then inserts the row with a timestamp.

If writing fails

The app rolls back, logs a short warning without details, and the user's request still succeeds.

Why the app can't edit the log

arcline_app has no privileges on audit_events (verified): it can't read, update or delete rows. It can only call the insert function. If an attacker took over the app, they still couldn't erase their tracks.

A trade-off to know: the "request still succeeds if the log write fails" rule favors keeping the app available over a complete audit trail. Some compliance standards require the opposite.

Event types: login_succeeded, login_failed, logout_succeeded, authentication_denied, role_authorization_denied, tenant_access_denied, document_access_succeeded, document_access_denied, scim_user_provisioned, scim_user_provisioning_denied. Code: main.py:152.

Least privilege

The four database roles

A PostgreSQL role is a database user. Each one gets only the permissions its job needs. Two of them can't even log in; they only own functions so those functions run with exactly their limited rights.

arcline_admin
can log inbypasses RLS

Runs migrations and creates test data. Never the app's role. If the app used it, wall 3 would silently switch off.

arcline_app
can log inRLS applies

What DATABASE_URL connects as (verified). SELECT on organizations, memberships, documents. EXECUTE on the audit and SCIM functions. Nothing on audit_events.

arcline_audit_writer
no loginINSERT only

Owns record_audit_event(). The only path into the audit table.

arcline_scim_writer
no loginone org only

Owns the four scim_*() functions. SELECT and INSERT on memberships, limited by its own RLS policies to the SCIM organization.

The SECURITY DEFINER pattern

Normally a function runs with the caller's rights. SECURITY DEFINER makes it run with the owner's rights instead. So the app gets a narrow door ("insert one valid audit row") without a key to the whole room. Each function also pins search_path so nobody can trick it into calling a fake table.

Understanding check

Check yourself

Answer in your head first, then open the answer.

Q1If DATABASE_URL connected as arcline_admin, which isolation wall would stop working, and why wouldn't the tests catch it?answer

Wall 3, RLS, because arcline_admin bypasses it. Walls 1 and 2 in Python would still block the leak, so every app test would still pass. The weakness only shows up if a future code change breaks walls 1 or 2.

Q2Why does SCIM always assign member and ignore any role in the request?answer

Otherwise anyone holding the SCIM token could create admins. The server decides privileges; the caller doesn't.

Q3An admin loses the admin role in Keycloak while still logged in. Can they still open /admin?answer

Yes, until they log out. Roles were copied into the session cookie at login and aren't re-checked with Keycloak on each request.

Q4What happens if the code forgets to call set_postgres_security_context before reading documents?answer

Zero rows come back. The empty setting becomes NULL, and comparisons with NULL never match. This is "failing closed": a bug hides data instead of exposing it.

Q5Why does the app never see the user's password?answer

With OIDC, the user types the password on Keycloak's page. The app only receives a one-time code, which it exchanges for a signed ID token.

Q6What's the difference between a 401 and a 403?answer

401: we don't know who you are (no or bad credentials). 403: we know who you are, and you're not allowed.

Q7How can the app write audit rows if it has no INSERT permission on audit_events?answer

It calls record_audit_event(), a SECURITY DEFINER function that runs with its owner's rights (arcline_audit_writer, INSERT only). The app gets one narrow door instead of table access.
